## 1. 文档职责

本文件定义一个仅服务单个用户的个人系统，统一管理学业、实习、秋招、邮件、日程、材料与必要的个人行动事项。

本文件是长期有效的“产品宪法＋分阶段路线”，用于约束后续 Agent 的产品判断。它只规定目标、体验、数据边界、自动化权限和阶段范围，不规定具体技术架构、数据库表、API 形状或供应商选型。

除非用户明确要求进入搭建阶段，Agent 只能继续梳理、验证和完善设计，不得编码、部署、连接账号或执行外部写入。

## 2. 已确认的用户背景

- 用户就读于香港大学 MFin，预计于 2027 年毕业。
- 产品永久作为个人工具，只服务该用户。
- 用户同时推进两条求职线：实习与秋招。
- 实习以香港为主、内地为辅，覆盖学期中实习、Off-cycle 和暑期实习。
- 秋招以内地为主、香港为辅，覆盖 Graduate Programme、应届 Analyst 和金融相关管培岗位。
- 用户使用 Gmail 作为全部邮件的集合与处理终端。
- 两个 163 邮箱和港大邮箱自行转发到 Gmail，产品不直接连接这些邮箱。
- 产品使用 Google Calendar 作为唯一外部日程系统。
- 用户拥有多个微信群，群内经常出现 JD、团队直招、内推和招聘线索。
- 产品使用中文界面，同时保留英文 JD、邮件、课程材料和简历原文，并支持双语摘要。

仍需在实际 onboarding 中由用户确认的运行时资料只有：

- 具体主攻、相邻和探索岗位方向
- 实习可入职日期、每周可工作天数和持续时长
- 工作资格、语言、技能及其他硬性条件
- 目标公司与招聘渠道清单

这些内容应由 AI 分析简历后提出建议，再由用户逐项确认；不得由实现者写死。

## 3. 产品定位

本产品是围绕港大 MFin 学业和双线求职构建的“个人机会操作系统”。

它持续回答：

- 今天有哪些固定安排和必须处理的事项？
- 学业、实习、秋招和个人事项发生冲突时，先做什么？
- 今天出现了哪些真正适合用户的实习与秋招岗位？
- 每个申请处于什么阶段，下一步是什么？
- 哪些邮件、微信信息、课程资料、材料和日程与当前行动相关？
- 哪些风险、断开的数据源或即将错过的窗口需要立即注意？
- 本周的求职和学习策略是否有效，应该如何调整？

统一闭环为：

> 信息进入 → 本地净化 → 理解与归类 → 形成上下文 → 生成行动 → 用户确认 → 同步执行 → 记录结果 → 复盘优化

## 4. 不可放宽的产品原则

### 4.1 单用户优先

- 不设计公开注册、团队空间、多人权限或商业化能力。
- 小组项目只管理用户自己的分工、团队里程碑和外部依赖。
- 不为课程组员或其他求职者提供协作账号。

### 4.2 今日行动优先

- 手机和电脑默认进入“今日行动”。
- 首页不是统计大屏，而是一份可在两分钟内读完的行动简报。
- AI 对话是解释、搜索和辅助操作入口，不承担主导航。

### 4.3 上下文与行动优先

- 邮件、日程、文件和任务必须尽量关联到课程、实习机会或秋招机会。
- 每个活跃机会应有明确的下一步行动。
- 系统必须区分等待用户、等待对方、无需行动和信息不足。
- 系统不能只记录截止日期，还要考虑准备成本、依赖和建议开始时间。

### 4.4 可解释与可追溯

- AI 推荐、过滤、归类、状态更新和自动写入必须给出依据。
- 所有关键结论保留原始来源、发现时间和最近核验时间。
- 低置信度内容进入待确认队列，不得静默猜测。
- AI 不得使用单一黑箱分数代替资格、匹配、意愿和紧迫度的分层解释。

### 4.5 人在关键决策回路中

AI 可以自动发现、提取、归类、分析、去重、整理和生成草稿，但以下动作必须由用户完成或明确确认：

- 发送邮件或微信消息
- 联系任何招聘人员、发布者或其他人
- 投递岗位或提交申请表
- 选择最终申请材料
- 接受、拒绝或签署 Offer
- 修改或删除用户原本创建的日程
- 永久删除重要数据

### 4.6 隐私最小化

- 只处理完成明确目标所需的数据。
- 原始敏感内容应优先在设备端净化，再上传必要数据。
- 不保存无关微信群聊天、无关成员信息或完整个人邮件正文。
- 凭据、验证码、邮件内容和材料不得出现在普通日志中。

### 4.7 覆盖诚实

- 系统可以提高岗位覆盖率，但不得声称找到“全部岗位”。
- 必须展示已覆盖、部分覆盖、需要用户导入和当前不可用的来源。
- 数据源失效时不得继续生成看似完整的报告。

## 5. 产品形态与视觉

### 5.1 双端形态

产品固定为：

- **iPhone 可安装 PWA**：从 Safari 添加到主屏幕，承担每日简报、推送、微信一键导入、快速决策、日程查看和移动记录。
- **电脑 Web App**：与 PWA 使用同一产品和账户，承担岗位比较、材料处理、课程工作区、详细计划和复盘。
- **统一云端账户与数据**：岗位、任务、材料、笔记、报告和同步状态在两端一致。

第一阶段不开发原生 iOS、Mac 或 Windows 客户端，不依赖 App Store、Mac/Xcode 或付费 Apple 开发者账号。

双端要求：

- 使用同一 Google 账户登录。
- iPhone 在系统支持时通过 Passkey/WebAuthn 调用 Face ID 或设备验证来解锁敏感内容。
- 移动端支持短暂离线并在联网后补同步。
- 两端修改应及时同步；同时编辑必须显式解决冲突，不能静默覆盖。
- 电脑端查看凭据、邮件和材料等敏感内容时应支持再次验证。
- 移动能力必须按 Safari/PWA 的真实边界设计；无法稳定实现的原生能力不得用界面伪装为已支持。

### 5.2 导航

主导航按行动优先组织：

1. 今日行动
2. 实习
3. 秋招
4. 学业

收件箱、材料、复盘、统一搜索和设置作为次级入口。系统提供跨模块统一搜索与快捷操作入口，可搜索岗位、申请、邮件摘要、课程资料、笔记、材料、日程和历史报告。

- 电脑端的实习、秋招和学业使用可排序、筛选的正式表格。
- iPhone 使用紧凑列表展示关键字段，点击后进入完整详情和时间线。
- 两端共享同一记录、字段、状态和历史。

### 5.3 视觉语言

- 风格定位为安静、克制、具有编辑感的高级个人工作台。
- 浅色主题为主，跟随系统自动切换深色主题。
- 主色方向为暖白、墨黑蓝、冷灰和低饱和深绿。
- 颜色主要表达状态，不为每个公司、课程或功能使用高饱和颜色。
- 避免金融终端式高密度、复杂渐变、过多阴影和滥用玻璃效果。
- 每个页面只突出一个主要问题，默认展示结论，需要时逐层展开细节。
- iPhone 强调快速阅读和单手操作；电脑端允许更高信息密度和并排比较。

### 5.4 设置与权限中心

设置是产品的固定入口。用户可以随时查看、开启、暂停、限时授权、断开和撤销所有可授权能力。

#### 权限层级

1. **AI 与自动化总开关**：关闭后停止 AI 分析、推荐和自动写入，但保留基础连接同步、已有数据查看和手动操作。
2. **分类开关**：Gmail、Google Calendar、求职雷达、微信导入、学业处理、文件、报告、通知和第二阶段浏览器自动化。
3. **细项开关**：邮件分析、个人事项提取、附件自动导入、岗位搜索与评分、状态自动更新、明确事实写入日历、排期建议和课程任务提取等。

首次使用时，重要权限默认关闭。每个开关必须先说明用途、读取或写入的数据、风险、依赖关系和最近使用时间，再由用户主动开启。

重要权限支持：

- 仅本次
- 24 小时
- 持续开启

限时授权到期后自动关闭，并取消尚未执行的相关任务。

#### 暂停、断开与数据

- 普通开关只暂停读取或自动化，保留第三方令牌。
- “断开账户”撤销第三方令牌，需要重新授权才能恢复。
- 关闭权限立即取消尚未执行的队列；正在运行的任务在最近安全点终止，并显示未完成结果。
- 暂停或断开默认保留已导入数据；另设按来源删除入口。
- 分类开关关闭时禁用全部子项并记住原状态；重新开启时展示将恢复的权限。
- 权限恢复后不得静默补跑全部历史任务，应先展示待补处理范围并由用户确认。

#### 隐私锁与身份验证

- 提供“一键隐私锁”，立即暂停 AI、外部读取、网络采集、同步和上传，但不删除历史数据。
- 解除隐私锁时必须重新验证身份。
- 断开账户、扩大权限、查看凭据、导出和永久删除需要 Passkey/设备验证或重新登录。
- 普通 AI 开关不要求重复验证。

所有权限变更进入审计记录。邮件发送、微信发送、联系他人、岗位投递和申请提交等禁止能力不得出现在权限列表中，也不能通过设置解锁。

## 6. 核心信息对象

### 6.1 机会 Opportunity

机会属于“实习”或“秋招”之一，可以是正式岗位、团队直招、内推或尚未形成标准 JD 的招聘线索。实习与秋招分别拥有独立的长期表。

AI 新发现的岗位先进入候选池。只有用户选择“追踪”或“申请”时，才在对应长期表创建正式记录；所有合格岗位不得自动塞入长期表。

至少记录：

- 公司、部门、岗位、地点和工作形式
- 所属求职线
- 岗位描述、要求、截止日期和招聘方式
- 来源、原始证据、首次发现和最近核验时间
- 资格、匹配、意愿和紧迫度
- 当前阶段、下一步行动和等待方
- 可选的发布者或招聘联系人信息
- 使用的材料版本和申请快照

主阶段固定为：

> 新发现 → 评估 → 准备 → 已投递 → 测试 → 面试 → 等待 → Offer → 结束

面试阶段允许一面、二面、技术面、HR 面等自定义子阶段，但不能改变主阶段体系。结束原因包括已拒绝、主动放弃、岗位关闭、资格不符和已过期。

实习表和秋招表的默认核心列为：

- 公司
- 岗位
- 地点
- 当前主阶段与子阶段
- 截止日期
- 投递日期
- 下一步行动与日期
- 下一场测试或面试
- 最近更新时间

主表只展示精简核心列。点击行后在详情侧栏查看来源与原始 JD、发现时间、资格与匹配分析、材料与申请快照、每轮测试和面试、邮件、日历事件、备注及完整发展时间线。

### 6.2 课程工作区 Course Workspace

学业拥有独立的长期表，每行代表一门课程，支持港大 MFin 的 Module 制度。每门课程同时拥有独立工作区。

学业表的默认核心列为：

- Module
- 课程名称与代码
- 上课起止日期
- 固定上课时段
- 任务完成率
- 手动课程状态
- 下一个截止日期
- 最近更新时间

课程主行自动计算任务完成率，同时允许用户手动标记“正常、需关注、落后、已结束”。展开课程行后查看：

- 课纲、课件、阅读材料和其他文件
- 作业、考试、Presentation、课程项目、用户自己的小组分工和其他课程事项
- 内置富文本笔记及外部笔记链接
- 任务完成情况和用户手动标记的掌握度
- 相关邮件、日程和来源

课程子任务记录名称、类型、发布日期、截止日期、完成状态、来源和 Google Calendar 关联，不记录成绩、分数或权重。

首次从课纲识别课程结构时必须由用户确认。确认后，港大邮件中高置信度的作业、考试和课程变更可以自动追加并通知用户。

### 6.3 沟通 Communication

包括 Gmail 邮件、微信导入内容、私聊记录和必要的会议笔记。

应识别：

- 所属课程、实习机会、秋招机会或个人事项
- 是否需要行动或回复
- 日期、截止、承诺和状态变化
- 来源身份、可信度和证据

### 6.4 行动 Action

每个行动包含：

- 清晰的可执行描述
- 所属上下文和求职线
- 截止时间、建议开始时间和预计耗时
- 优先级、依赖和完成标准
- 已排期、未排期、等待或完成状态

### 6.5 材料 Artifact

包括 Master CV、岗位派生简历、Cover Letter、成绩单、在读证明、项目素材、申请答案、课程资料和笔记附件。

Master 材料只读，AI 不得覆盖原件。每次申请保存独立快照：

- 当时的 JD
- 提交使用的所有材料
- 申请表答案
- 提交时间和申请编号
- 来源、推荐或内推信息

### 6.6 事件 Event

包括课程、考试、面试、宣讲、截止日期、准备时间块和个人重要事项。事件必须与 Google Calendar 中的对应事件保持稳定关联，避免重复。

### 6.7 长期跟踪表通用规则

实习、秋招和学业三张表均采用：

- 固定核心字段＋用户自定义字段
- 精简核心列＋详情侧栏
- 当前状态＋追加式发展时间线
- 进行中与已归档视图
- 排序、筛选、搜索和保存视图

自定义字段可以是文本、日期、选项、评分或链接，但不得覆盖或破坏系统核心状态。

每次发现、追踪、投递、测试、面试、课程任务、状态变化、备注、材料和 Calendar 关联都追加到时间线，更新当前状态时不得覆盖历史。

用户手动修改过的字段自动锁定。AI 发现新证据与锁定字段冲突时，只能提出带来源的修改建议；除非用户解除锁定或确认修改，否则不得覆盖。

高置信度自动更新必须通知、写入审计记录并提供撤销。低置信度变化进入待确认队列。

## 7. 每日行动与报告

### 7.1 晨间简报

- 默认每天 08:00 生成，用户可以修改时间。
- App 推送只显示一句摘要，完整内容在应用内展示。
- 报告展示最后更新时间和数据源健康状态。

内容顺序：

1. 今日固定日程
2. 必须处理的事项
3. AI 推荐的三个重点及原因
4. 实习重点岗位，最多 5 个
5. 秋招重点岗位，最多 5 个
6. 需要处理的邮件与沟通
7. 风险、冲突和失效数据源
8. 已确认安排与待确认时间块

每条求职线不足 5 个高质量岗位时宁缺毋滥，不得用低质量岗位凑数。

### 7.2 白天即时提醒

只有以下情况允许即时推送：

- 收到面试邀请
- 事项将在 24 小时内截止
- 出现明确日程冲突
- 出现高度匹配且时效很短的机会
- 关键连接或自动化持续失效

其他变化进入下一份报告，避免通知过载。

### 7.3 晚间收尾

- 默认每天 22:30 生成，用户可以修改时间。
- 用一分钟处理完成、继续、重排、等待、取消或降级。
- 未完成事项不得无脑滚动到第二天。
- 新的 AI 建议时间块仍需用户确认。

### 7.4 每周复盘

- 默认周日 20:00 生成，用户可以修改时间。
- 汇总学业负荷、实习进度、秋招进度、下周截止、来源覆盖和策略风险。
- 用户确认下周计划后，相关时间块才同步到 Google Calendar。

## 8. Google Calendar 规则

Google Calendar 是唯一外部日程数据源、每日事项历史、执行界面和事件提醒系统。产品内部提供智能计划视图，但不重建完整日历基础设施。三张长期表保存完整发展历史，Google Calendar 只负责每天的事项、时间和提醒。

### 8.1 日历结构

- 使用一本由个人 Google 账户持有的统一产品日历。
- 有具体时间的事项同步为时间事件。
- 只有日期、没有具体时间的当天事项同步为全天事件。
- 未安排到某一天的候选任务仍只存在产品中。
- 不使用 Google Tasks。
- 所有当日事项长期保留，不因完成或取消而静默删除。
- 读取用户 Google Calendar 中全部已有事件详情，用于报告和冲突判断。

分类标签固定为学业、实习、秋招和个人。每类使用低饱和高级默认色，并允许用户在设置中修改。使用同一本日历的事件标签实现标题与颜色双重区分；实现依据参见 [Google Calendar 官方标签说明](https://developers.google.com/workspace/calendar/api/guides/labels)。

标题格式：

- 未完成：`类别｜事项名称`
- 已完成：`✓ 类别｜事项名称`
- 已取消：`已取消｜类别｜事项名称`

完成状态以产品为操作入口。用户在 App 或 Web 标记完成后，Calendar 事件更新标题并长期保留。

### 8.2 写入权限

- 邮件或课纲中明确的面试、考试、课程变更和截止日期，在高置信度时可自动写入并通知用户。
- AI 建议的学习、申请和准备时间块必须先由用户修改或确认，再批量写入。
- 产品创建的事件可以双向同步和重新排期。
- 修改或删除用户原本创建的事件必须逐项确认。
- 同步失败、权限失效和冲突必须显式展示，不得静默丢失。
- 当 Calendar 写入权限暂停时，三张表继续更新，新行动日期标记为“待同步”，不得尝试写入。

### 8.3 三张表与 Calendar

- 三张表是岗位和课程发展历史的真相源。
- 面试、测试、考试、课程、截止和需要当天执行的任务同步到 Calendar。
- 普通状态变化、材料、评分、备注和完整时间线不写入 Calendar。
- Calendar 事件详情包含返回对应岗位、课程或任务的产品入口。
- 用户在 Calendar 删除与表格关联的事件时，产品提示“取消排期或重新同步”，不得静默重建，也不得删除表格历史。
- 表格中的状态变化与 Calendar 中的完成标记保持一致，但 Calendar 不承担长期跟踪逻辑。

### 8.4 排期与提醒

- AI 排期只强制避开已有事件，不预设睡眠、用餐或最大专注时长。
- 所有建议计划必须允许用户修改。
- 事件开始、提前提醒和重复提醒由 Google Calendar 负责。
- App 只负责日报、风险、高价值机会和连接异常等智能提醒。

## 9. Gmail 入口与邮件边界

### 9.1 唯一入口

产品只连接 Gmail。其他邮箱继续自行转发至 Gmail：

- `job-forward` 来源：只用于求职相关邮件和文件。
- `personal-forward` 来源：非求职个人重要邮件。
- 港大邮箱来源：学业和校内相关信息。

系统应通过转发头、原始收件地址和发件来源恢复邮件归属，不能把所有邮件视为同一身份。

### 9.2 邮件保存

- 求职和学业邮件保存摘要、行动项、必要证据片段和 Gmail 原邮件链接。
- 非求职个人邮件只提取行动和日期，不进行长期全文分析。
- 产品不复制完整 Gmail 邮箱。
- 高置信度相关附件可以自动导入产品，但必须通知、说明归类依据，并允许立即删除。

### 9.3 草稿与发送

- AI 可以生成可编辑邮件草稿。
- 草稿必须标注应使用的原邮箱身份。
- 用户可以修改、复制或打开草稿。
- 产品绝不能发送、转发或自动回复邮件。
- Gmail 消息本身按只读处理；不得自动归档、删除、加标签或改变已读状态。
- 若未来允许在 Gmail 创建草稿，也只能创建或更新草稿对象，不得调用发送能力。

### 9.4 验证码

第二阶段的只读浏览器自动化可以从已授权 Gmail 中识别一次性登录验证码并继续登录。

- 验证码不得长期保存、进入日报、普通日志或 AI 长期上下文。
- 验证码不得转发。
- 短信验证码、设备确认和异常风控必须由用户亲自完成。

## 10. AI 求职雷达

### 10.1 双线模型

实习与秋招必须使用两条独立管道：

- 分别维护岗位池、评分、材料、状态、统计和日报区块。
- 共享基础经历、技能和 Master 材料。
- 每条线每天分别展示最多 5 个重点岗位。

### 10.2 岗位画像

AI 首先分析简历与经历，分别为两条线提出：

- 主攻方向
- 相邻方向
- 探索方向
- 排除方向和硬性条件

用户确认后才用于搜岗。后续行为可以影响排序，但不得静默改变已确认方向。

### 10.3 发现策略

岗位发现采用“重点渠道＋全网补充”：

1. 用户确认的目标公司官网
2. 用户确认的主要招聘平台
3. 港大招聘、学院邮件和校园信息
4. 微信一键导入
5. 公开网络补充搜索

初始公司和渠道清单由 AI 提议，用户审核后启用。系统可以建议增加来源，但不得静默扩大自动登录或采集范围。

### 10.4 清洗与评分

系统应完成：

- 标准化岗位字段
- 跨渠道去重
- 保存官方链接和有价值的补充来源
- 核验岗位是否仍开放
- 区分同名但不同团队的职位
- 识别资格不符、失效、销售导向或明显低质量岗位

评分必须分别展示：

- 资格：能否申请
- 匹配：背景是否吻合
- 意愿：是否符合方向和偏好
- 紧迫：是否需要立即行动

每个推荐还要解释准备成本、主要缺口、风险和建议下一步。

### 10.5 用户决策与申请权限

核心选择：

- 追踪
- 申请
- 稍后判断
- 不考虑并记录原因

新岗位默认留在候选池。只有用户选择“追踪”或“申请”时，才进入对应的实习或秋招长期表，并从该时点开始保存评估、准备和申请历史。

AI 可以：

- 分析 JD
- 推荐材料版本
- 生成派生材料
- 草拟申请题答案
- 建立申请计划

AI 不得：

- 联系任何人
- 打开提交行为或代表用户投递
- 提交申请表
- 修改招聘平台个人资料
- 接受任何条款或声明

用户必须亲自检查并提交申请。

### 10.6 状态自动更新

- 明确的笔试、面试、拒信和 Offer 邮件可在高置信度时自动更新管道。
- 每次自动更新必须展示原邮件证据、通知用户、写入审计记录并提供一键撤销。
- 不确定内容必须进入待确认队列。

## 11. 微信能力退役

用户于 2026-11-11 决定永久移除全部微信功能，不再提供自动雷达、OCR、分享或微信专用导入。历史岗位、来源证据及审计可读保留；运行权限、接口和自动任务必须拒绝新的采集或导入。下文历史场景中的微信要求已被 D25 替代，不作为验收或重建依据。

## 12. 完整学习系统

### 12.1 课程工作区

学习系统以课程为核心，不以聊天或跨课程知识图谱为主入口。

最终能力包括：

- 课纲、课件、阅读和其他课程资料
- 课程任务、作业、考试、Presentation 和个人小组分工
- 内置富文本笔记，支持文字、公式、图片和文件引用
- 外部笔记工具的链接或导入入口
- 任务进度和用户手动掌握度
- 搜索、标签、分类和来源定位
- 学业事项与 Google Calendar 联动

### 12.2 信息进入方式

第一版采用：

- 上传课程课纲
- 从转发到 Gmail 的港大邮件提取变化
- 用户手动修正或补充

第一版不直接连接学校教学平台。

### 12.3 学习 AI 边界

学习 AI 只负责：

- 摘要
- 标签
- 分类
- 检索
- 来源定位
- 资料与课程事项关联

学习 AI 不负责：

- 充当课程讲师
- 生成练习题或模拟考试
- 代写作业
- 自动完成学习任务
- 仅凭浏览时间判断用户已经掌握

进度由任务完成情况与用户手动掌握度共同构成。

## 13. 个人事项

- 非求职、非学业的重要个人邮件可以提取行动和日期。
- 相关行动可以进入日报，并在明确或确认后写入 Google Calendar。
- 不建立独立生活管理模块。
- 不对个人邮件进行深度全文分析。

## 14. 收件箱、搜索与系统状态

### 14.1 统一收件箱

微信导入、邮件行动、课纲和上传文件进入统一收件箱：

- 高置信度内容自动归类到学业、实习、秋招或个人事项。
- 模糊内容保留在待确认队列。
- 自动归类必须进入操作记录并支持纠正。

### 14.2 统一搜索

搜索覆盖：

- 岗位与申请
- 邮件摘要和证据片段
- 课程资料与笔记
- 材料和申请快照
- 日程与报告

搜索结果必须遵守原对象的权限和隐私边界。

### 14.3 连接与自动化状态中心

集中展示：

- Gmail、Google Calendar、岗位来源、微信一键导入和已获批准的本地监测状态
- 最近同步与最近成功采集时间
- 覆盖范围和当前缺口
- 失败原因、重试状态和重新授权入口
- 浏览器自动化的当前权限和会话状态

### 14.4 AI 操作与撤销中心

完整记录：

- AI 何时执行了什么操作
- 使用了什么来源和判断依据
- 操作结果、失败和后续影响
- 可逆操作的撤销入口

敏感凭据和验证码不得写入审计内容。

### 14.5 权限与三张表的联动

- Gmail 分析关闭：保留历史表格，但停止从新邮件更新状态。
- Google Calendar 写入关闭：表格继续更新，新行动日期显示“待同步”。
- 岗位雷达关闭：停止发现新候选，不影响已追踪岗位。
- 自动状态更新关闭：新证据进入待确认，不自动改变主表。
- 学业自动提取关闭：课纲和邮件仍可手动导入，但不自动新增任务。
- 附件自动导入关闭：只显示 Gmail 原附件链接。
- 隐私锁开启：三张表只读，所有外部访问和自动化立即暂停。
- 权限重新开启后不得自动补跑全部历史任务；先展示待补处理范围，由用户确认后执行。

### 14.6 固定状态语义

- 连接状态：`已连接 / 已暂停 / 已断开 / 异常`
- 权限授权：`关闭 / 仅本次 / 限时至某时间 / 持续开启`
- 自动化状态：`空闲 / 运行中 / 已暂停 / 已取消 / 失败`
- 跟踪领域：`实习 / 秋招 / 学业`
- 表格记录状态：`进行中 / 已归档`
- Calendar 同步状态：`已同步 / 待同步 / 冲突 / 失败`
- 字段来源：`用户手动 / AI 提取 / Gmail / Calendar / 微信 / 公开来源`

用户手动修改过的字段附带锁定标识，除非用户解除锁定或确认 AI 建议，否则 AI 不得覆盖。

## 15. 数据、文件与安全

### 15.1 处理模型

- 原始敏感内容优先在设备端净化。
- 必要结构化数据和文件加密上传云端。
- 云端负责双端同步、搜索、材料版本和 AI 分析。
- 传输、静态存储和备份均需加密。

### 15.2 产品内文件存储

- 简历、申请材料、课程资料和笔记附件直接存入产品。
- 支持版本历史、申请快照和单文件恢复。
- Master 材料不可被 AI 覆盖。

### 15.3 保留、删除与备份

- 数据默认长期保留。
- 每日执行加密备份，并支持单文件、课程工作区和全系统版本恢复。
- 普通删除进入 30 天回收站。
- 用户可以立即永久删除或完整导出全部数据。
- 登录凭据删除后立即从凭据保险库清除，不进入普通回收站。
- 备份必须遵守永久删除与保留规则。

## 16. 第二阶段只读浏览器自动化

受限招聘平台的自动登录采集不进入第一阶段。

### 16.1 允许行为

- 使用加密保存的账号密码登录
- 使用已授权的现有会话
- 搜索、读取、翻页、提取、核验和去重岗位信息
- 从已授权 Gmail 中读取一次性邮箱验证码并继续登录

### 16.2 绝对禁止行为

- 联系或发送消息
- 投递或提交申请
- 收藏、关注或创建平台提醒
- 修改个人资料、简历或偏好
- 接受条款、签署声明或执行其他平台写入
- 绕过验证码、风控或访问限制

遇到短信验证、设备确认、异常风控或任何无法确认是否只读的步骤时，自动化必须停止并交给用户。

### 16.3 凭据保险库

- 招聘平台账号密码以最高敏感等级独立加密保存。
- 凭据与普通业务数据分离。
- 凭据不得进入 AI 上下文、普通日志、报告、导出预览或分析数据。
- 用户可以查看授权范围、撤销会话和立即删除凭据。

## 17. 分阶段路线

### 第一阶段：核心闭环

- iPhone 可安装 PWA 与电脑 Web App
- Google 登录、Passkey/设备再验证和云端同步
- 设置与权限中心、临时授权、连接暂停/断开和一键隐私锁
- 今日行动、晨报、晚间收尾和周报
- Gmail 单一入口及邮件归类
- Google Calendar 全量每日事项、分类标签、完成历史和双向同步
- 实习、秋招、学业三个独立一级入口与长期跟踪表
- 实习与秋招双线岗位雷达
- 重点渠道、公开网络、Windows 微信白名单群自动监测与一键导入兜底
- 统一收件箱、统一搜索、状态中心和审计中心
- 产品内材料存储、Master 与岗位派生版本
- 申请管道、高置信度状态更新和撤销
- 课程工作区、课纲解析、任务、资料、基础富文本笔记和手动掌握度

第一阶段求职闭环到“岗位发现—筛选—材料准备—用户提交—申请追踪”，不包含受限平台自动登录、模拟面试或 Offer 比较。

### 第二阶段：高级自动化与准备

- 受限平台只读浏览器自动化
- 加密凭据保险库和邮箱验证码读取
- 高级课程资料整理
- 外部笔记工具连接
- 面试简报
- 岗位化题库
- 文字或语音模拟面试与复盘

### 后续增强

- 实习与秋招完整漏斗分析
- 来源渠道、岗位方向和材料版本效果比较
- 多 Offer 的岗位内容、平台、薪酬、地点、发展、风险与期限比较

## 18. 成功标准

- 重要学业、实习、秋招和个人截止不再遗漏。
- 用户每天能在两分钟内明确当天重点。
- 高价值机会从发现到行动的时间缩短。
- 实习与秋招信息始终清晰分开。
- 实习、秋招和学业均能通过独立长期表查看当前状态与完整发展时间线。
- 邮件、微信、材料和日程能回到同一课程或机会上下文。
- 用户清楚知道 AI 为什么推荐、过滤或自动更新某项内容。
- 每天所有已指定日期的事项都可靠地进入 Google Calendar，并长期保留完成或取消历史。
- 用户能够随时查看、暂停、限时开启、断开或撤销重要权限。
- 微信高时效机会能在 Windows 运行条件满足时由白名单群自动雷达捕捉，并可用一键导入补漏；不得上传或长期保存无关聊天。
- 系统能显示来源覆盖和连接异常，不制造虚假的完整感。
- 系统减少认知和录入负担，而不是产生新的维护工作。

## 19. 场景验收

### 19.1 微信 JD

> 白名单群出现 JD → Windows 本地自动增量识别与净化（或用户一键导入补漏）→ 保留必要来源 → 进入候选池 → 用户选择追踪 → 创建实习或秋招表记录 → 行动日期同步 Calendar → 准备岗位材料 → 用户亲自提交

验收点：非白名单群不读取；无关聊天不上传或长期保存；不发送微信；不自动投递；来源可检索；未选择追踪的岗位不进入长期表；未运行时明确显示覆盖缺口。

### 19.2 面试邮件

> Gmail 收到面试邮件 → 提取证据 → 高置信度更新岗位主状态和追加时间线 → 自动创建面试事件 → 通知用户 → 写入审计记录并允许撤销

验收点：邮件不自动回复；原邮件可追溯；日程不重复；表格历史不被覆盖；低置信度进入待确认。

### 19.3 课程课纲

> 上传课纲 → 用户确认课程结构 → 创建学业表课程行 → 高置信度任务和考试自动追加 → 进入日报 → AI 提议准备时间块 → 用户确认 → 写入 Google Calendar

验收点：首次建课必须确认；用户可以修正提取结果；建议时间块不自动写入；课程资料可搜索；学业表不记录成绩。

### 19.4 个人邮件

> 非求职个人邮件进入 Gmail → 只提取行动和日期 → 进入日报 → 明确事实自动同步或建议事项等待确认

验收点：不保存完整正文；不进行深度个人内容分析。

### 19.5 权限中途关闭

> 自动化正在处理邮件或岗位 → 用户关闭对应权限 → 取消排队任务 → 当前任务在安全点停止 → 三张表历史保留 → 状态中心显示暂停原因

验收点：关闭后无新的读取或写入；恢复时不静默补跑历史；权限变更可审计；隐私锁停止全部外部访问。

### 19.6 完成事项

> 用户在产品中完成事项 → 对应表格或任务更新 → Calendar 事件保留 → 标题增加完成标记 → 历史仍可检索

验收点：完成事件不删除；Google Calendar 不作为长期表真相源；两端状态一致。

## 20. Agent 工作规则

后续 Agent 必须：

- 先判断请求属于第一阶段、第二阶段还是后续增强。
- 明确区分已确认规则、运行时用户资料和待设计的技术实现。
- 优先设计端到端闭环，不堆砌孤立功能。
- 每项功能说明输入、判断、输出、用户确认点、失败处理和审计方式。
- 所有推荐和自动行为保留来源与解释。
- 涉及 Gmail、Google Calendar、微信、凭据或文件时遵守最小权限。
- Windows 微信监测已获用户批准纳入 M7；实施必须限制为本机白名单群、先本地净化、只读、低频、可立即停止且覆盖状态可见。
- 在执行任何自动化前检查全局、分类、细项和临时授权状态；权限关闭或到期后立即停止。
- 权限恢复后不得自行补跑暂停期间的历史任务。
- 实习、秋招和学业的长期状态必须写入对应产品内表格；Google Calendar 只承载每日事项和提醒。
- 用户手动锁定字段不得被 AI 自动覆盖。
- 不得将“高置信度”解释为可以突破邮件发送、微信发送、申请提交或平台只读边界。
- 未经用户明确授权，不执行账号连接、消息发送、岗位投递或外部数据写入。
- 进入实施阶段后，将具体架构、数据模型、API、权限、测试和迁移计划写入独立实施文档，不把易过时的技术细节塞回本文件。

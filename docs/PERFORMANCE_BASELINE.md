# 性能基线与 #10 快修记录

更新：2026-11-12。口径见 D32：列表页数据库往返批次 ≤ 2；首页服务端耗时 p75 ≤ 1.0 秒（隔离 Test、开发者所在网络）；200 行列表载荷 ≤ 200 KB。

## 1. 如何测量

- **服务端耗时与往返**：本地开发时在 `apps/web/.env.local` 加 `MFIN_DEBUG_TIMING=1`，连接自己的隔离 Test 项目（不能用 mock 模式）。每次 Supabase 调用会输出一行 `[mfin-timing] GET v1/opportunities 200 84ms`，只含方法、表或 RPC 名、状态码和耗时，不含查询参数或数据。一次页面加载的行数即调用次数，时间上重叠的行属于同一批次。
- **列表载荷**：`pnpm perf:payload` 用合成种子（200 个岗位）计算列表查询返回的 JSON 大小，改动前后口径一致。
- **查询计划**：在本地 PostgreSQL 集成环境（`pnpm test:db` 使用的同一套迁移与种子）中以 `authenticated` 身份 `EXPLAIN ANALYZE`。

## 2. 列表载荷（合成种子，`pnpm perf:payload`）

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 实习列表 | 100 行、190.6 KB（`select *`，含归档，含 JD 原文） | 50 行、16.6 KB（列表列、仅进行中、第一页） |
| 秋招列表 | 100 行、191.0 KB | 50 行、16.6 KB |
| 同一条线 200 行（仅换列） | 347.0 KB | 63.2 KB，满足 ≤ 200 KB |

## 3. 每页数据库批次（按代码统计）

| 页面 | 改动前 | 改动后 |
|---|---|---|
| 实习 / 秋招列表 | 1 批 8 个查询；全部行取回后在 Node 端筛选、排序 | 1 批 8 个查询；阶段、归档、关键词、排序与分页（每页 50 行）在数据库完成 |
| 岗位详情 | 详情 1 批，之后简历、投递包、快照再 1–2 批 | 详情、简历、投递包、快照合并为 1 批；投递包条目再 1 批 |
| 收件箱 | 1 批 7 个查询（含退役的微信投影与截图两张表） | 1 批 5 个查询；只有存在历史微信条目时才按 ID 补 1 批（D25，数据保留） |
| 所有登录页面 | layout 与页面各解析一次登录凭据 | `cache()` 合并为每请求一次 |

## 4. 查询计划

列表主查询（实习、进行中、按更新时间、前 50 行）使用既有索引 `opportunities_track_state_idx (user_id, track, record_state, updated_at desc)`，200 行种子下执行 0.09 ms。现有索引已覆盖本次所有列表查询，因此不新增索引迁移。
